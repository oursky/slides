// helm · which chart

Standalone, or replication?

mode · A

Standalone

failure → pod restarts
  • One pod. No replicas. No sentinel.
  • Simple config, fast to deploy, easy to reason about.
  • Downtime window while the pod restarts.
  • In-memory data is gone unless persisted to a volume.
→ caches · dev · stateless-ish workloads
mode · B

Replication

failure → sentinel promotes replica
  • Master + replicas + sentinel quorum, all orchestrated.
  • Seconds to new master — failover under the app.
  • More moving parts. More config. More to understand.
  • Needs HAProxy (or sentinel-aware client) for seamless access.
→ anything we can't afford to lose
part 03 / 03
// 12 · pattern
// the takeaway

Same shape,
every time.

01 · redundancy

More than one node.

Primary + standby. Master + replicas. Never a single box holding state.

02 · consensus

A quorum picks the leader.

Sentinels vote. Health-check majorities decide. No humans in the loop.

03 · access point

One stable endpoint.

The app connects to a proxy. The proxy hides which node is leading today.

Our code can be perfect — but only if the foundation is too.
